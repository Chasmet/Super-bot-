# Audit Super Bot — 5 septembre 2026

Périmètre : tous les 31 fichiers du dépôt à `0d820203bc801babaa24a11ac759e53af0758503` (13 classes Java, manifeste, ressources et compilation), historique de compilation, APK publics 1.2.1 et 1.2.4. Analyse statique : aucun téléphone connecté, aucune session réelle TikTok/Instagram/YouTube testée.

## Incident de mise à jour : cause démontrée

Les certificats des deux APK publiés diffèrent, selon `keytool -printcert -jarfile` :

| Version | SHA-256 du certificat |
| --- | --- |
| 1.2.1 | 99:E8:E2:65:27:C3:D7:DC:0F:94:9F:50:14:57:A2:FB:CC:8E:5D:47:AC:02:8E:B6:14:73:DE:50:38:93:DE:FF |
| 1.2.4 | F3:2C:4D:A8:EB:83:D5:FF:DF:40:36:D9:ED:48:2A:E4:07:5C:40:17:44:A2:96:B6:2E:77:90:0E:A2:48:35:0F |

Le cache déclaré dans le workflow n'a donc pas assuré une identité constante des APK. La raison exacte de cette divergence dans les anciennes exécutions reste à établir. Une signature différente suffit à empêcher une mise à jour normale. Le certificat de l'installation réelle n'a pas été extrait du téléphone ; la capture indique 1.2.1.

La correction impose une configuration Gradle de signature explicite, avec copie de la clé restaurée hors des caches Gradle. Avant publication, apksigner vérifie le nouvel APK et compare son certificat à l'APK 1.2.1. Une divergence bloque la release. Aucun changement d'applicationId ni effacement de données.

**Condition indispensable : retrouver la clé privée correspondant au certificat 1.2.1.** Une nouvelle clé, une modification du versionCode ou une nouvelle autorisation Android ne peuvent pas remplacer cette condition. Ne pas désinstaller pour contourner l'erreur.

## Limites restantes de l'application

Ces points sont des résultats d'audit, pas des fonctionnalités présentées comme réparées :

- **Clé de signature** : un cache Actions n'est pas une sauvegarde durable. Conserver la clé originale dans un secret de signature durable reste nécessaire ; aucune clé privée n'est ajoutée au dépôt ni aux artifacts.
- **TikTok** : la date est recherchée avec le seul numéro de jour, sans validation du mois/année ; les roues reposent sur des heuristiques de texte et de défilement. La date complète et le résultat doivent être vérifiés sur l'interface réelle. Les boucles n'ont pas de délai d'abandon global.
- **Autres réseaux** : Instagram et YouTube utilisent des alarmes et un moteur générique, pas une programmation native immédiate. X n'est pas implémenté. MCP est un écran d'attente, les boutons affichent des messages.
- **Concurrence des missions** : un seul `active_task_id` peut être écrasé par une autre mission. Il manque un ordonnanceur exclusif avec reprise de file.
- **Alarmes** : les tâches échues pendant un arrêt sont ignorées au redémarrage ; le démarrage d'une activité en arrière-plan peut être refusé par Android. `hashCode()` ne garantit pas un identifiant PendingIntent unique. Supprimer une mission ne supprime pas son alarme (le receiver retrouve néanmoins une tâche absente et ne publie pas).
- **Visibilité** : la visibilité choisie est enregistrée mais le moteur ne l'applique pas aux réseaux.
- **Vidéo** : découpage sans réencodage, avec suppression des échantillons précédant le début demandé : risque de commencer sur une image dépendante non décodable. Rotation de la source non copiée, tampon fixe de 2 Mo, erreurs de finalisation du muxer ignorées. Une coupe exacte doit être réencodée ou explicitement alignée sur une image clé.
- **Cycle de vie studio** : extraction de durée sur le thread UI, état du média non restauré après recréation, interruption de l'executor non vérifiée dans le découpage.
- **Stockage** : données de tâches conservées dans SharedPreferences ; JSON malformé silencieusement interprété comme une liste vide. Pas d'export/import explicite pour migration. Les vidéos sont dans le stockage propre à l'application et peuvent disparaître après désinstallation.
- **Sécurité et permissions** : FileProvider non exporté, activités internes non exportées, service protégé par BIND_ACCESSIBILITY_SERVICE. Aucune clé d'API nécessaire à l'automatisation locale. Les publications réelles restent à vérifier, notamment les textes de confirmation trop génériques.
- **Construction** : wrapper incomplet (fichier properties seul, absence de gradlew/jar). CI utilise Gradle 8.9 installé par setup-gradle. Aucun test automatisé existant dans la version auditée.

## Validation

- Diff : `git diff --check` sans erreur.
- Certificats des APK publics : divergence vérifiée localement, valeurs ci-dessus.
- Premier passage CI : assembleDebug réussi ; Lint a trouvé 2 erreurs préexistantes (windowLightStatusBar API 23, indicateurs MediaExtractor transmis directement à MediaCodec). Les deux erreurs ont été corrigées sans désactiver Lint.
- Les 133 avertissements du premier passage concernent surtout les textes codés en dur (109), la présentation et les suggestions de version des dépendances/SDK. Le targetSdk 34 demandé est conservé.
- Résultat final : voir les exécutions Actions liées à la PR ; ne pas confondre compilation réussie et installation compatible.
- Contrôle de signature : gate apksigner ajouté ; le résultat du test est requis avant publication.
- `./gradlew assembleDebug` n'a pas été exécuté : wrapper absent et aucun SDK Android local. La commande CI est `gradle assembleDebug lintDebug`.
- Aucun résultat d'installation sur le téléphone ni de programmation réelle sur les réseaux n'est affirmé.
